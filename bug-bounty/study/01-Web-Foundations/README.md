# 🔵 STAGE 1 — WEB FOUNDATIONS

## Professional Web Security Fundamentals

---

# 1. Stage Overview

Stage 1 establishes the technical foundation required to understand and analyze modern web applications.

The objective is not to memorize vulnerability names.

The objective is to understand how web applications communicate, how browsers process web content, how applications manage identity and state, and where trust boundaries exist.

A security researcher should be able to look at a web application and understand:

```text
Who is communicating?
What is being requested?
Where is the request going?
What data is being transmitted?
How is identity represented?
How is authorization enforced?
Where is data processed?
What assumptions does each component make?
Where does trust change?
```

Stage 1 therefore focuses on the underlying technology that later vulnerability classes depend upon.

---

# 2. Stage Objectives

By completing Stage 1, the researcher should be able to:

* Explain the client/server model.
* Explain the basic lifecycle of a web request.
* Understand HTTP requests and responses.
* Identify important HTTP methods and status codes.
* Read and interpret HTTP headers.
* Understand cookies and session concepts.
* Distinguish authentication from authorization.
* Understand URLs, parameters, and encoding.
* Understand fundamental HTML and DOM concepts.
* Understand JavaScript's role in web applications.
* Understand browser security boundaries.
* Explain the Same-Origin Policy.
* Understand the purpose and mechanics of CORS.
* Describe common web application architectures.
* Understand basic APIs and JSON.
* Understand proxies and intermediaries.
* Develop a security-oriented mental model of web applications.

---

# 3. Learning Philosophy

Stage 1 follows:


# 1.12 — Same-Origin Policy

## Objective

Understand the browser security boundary based on origins.

An origin is generally determined by:

```text
scheme + host + port
```

For example:

```text
https://example.com
```

has:

```text
scheme = https
host   = example.com
port   = 443
```

## Topics

* Origin.
* Same-origin.
* Cross-origin.
* Scheme differences.
* Host differences.
* Port differences.
* Browser enforcement.

## Practical Exercise

Classify controlled examples as same-origin or cross-origin.

## Completion Criteria

Correctly determine whether two URLs have the same origin.

# 1.17 — Web Security Mental Models

## Objective

Combine the preceding concepts into a security-oriented way of analyzing web applications.

For every request, ask:

```text
WHO?
 ↓
WHAT?
 ↓
WHERE?
 ↓
WHEN?
 ↓
HOW?
 ↓
TRUSTED BY WHOM?
 ↓
VALIDATED WHERE?
 ↓
AUTHORIZED WHERE?
 ↓
ENFORCED WHERE?
```

## Security Questions

For any controlled application, consider:

### Identity

Who is making the request?

### Input

What data is being supplied?

### Trust

Which component trusts that data?

### Processing

Where is the data processed?

### Authorization

Who is allowed to perform the action?

### Validation

Where is the data validated?

### Output

Where does the resulting data appear?

### State

What identifies the current session or user?

### Boundary

Where does trust move from one component to another?

## Practical Exercise

Take one request from a controlled application and document:

```text
Client
 ↓
Request
 ↓
Authentication
 ↓
Authorization
 ↓
Validation
 ↓
Processing
 ↓
Database / service
 ↓
Response
 ↓
Browser
```

Identify every trust boundary you can observe.

## Completion Criteria

Demonstrate that you can reason about a web request without immediately jumping to a specific vulnerability.

# 10. Stage 1 Operating Rules

1. Understand the technology before testing it.
2. Use controlled environments for practical exercises.
3. Do not assume reachability means authorization.
4. Do not test real systems merely because they are accessible.
5. Keep learning exercises reproducible.
6. Record observations rather than guessing.
7. Separate facts from assumptions.
8. Do not collect unnecessary sensitive data.
9. Commit meaningful project milestones.
10. Ask "why?" rather than memorizing commands.

# 14. Stage 1 → Stage 2 Transition

Stage 2 introduces Burp Suite as a dedicated manual testing environment.

The transition should occur only after the researcher can comfortably answer:

> What am I looking at?

when presented with an HTTP request or response.

Stage 2 then focuses on:

```text
Browser
   ↓
Burp Suite
   ↓
HTTP request
   ↓
Application
   ↓
HTTP response
   ↓
Burp Suite
   ↓
Browser
```

Stage 1 provides the conceptual foundation.

Stage 2 provides the interception and analysis workflow.

# 15. Final Stage 1 Principle

The purpose of Web Foundations is to replace:

```text
"What tool should I run?"
```

with:

```text
"What is the application doing?"
```

A strong web security researcher does not begin with a payload.

They begin with an understanding of:

```text
Architecture
 ↓
Communication
 ↓
Identity
 ↓
State
 ↓
Trust
 ↓
Authorization
 ↓
Data flow
 ↓
Application behavior
```

Only then does vulnerability-specific testing become meaningful.

**Stage 1 is the foundation for understanding the web application before attempting to understand how it can fail.**
